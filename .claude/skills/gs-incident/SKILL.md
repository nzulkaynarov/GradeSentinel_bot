# /gs-incident — от симптома до PR

1. **Таймлайн.** `make prod-grep TAG='<ключевые теги>'` за нужный период (`journalctl --since/--until`,
   время Ташкента). Зафиксировать: когда монитор увидел, когда подтвердил ([PENDING] → [NEW GRADE]),
   куда ушло (`ntype=... status=...`), были ли рестарты (`Started/Stopped`).
2. **Улики в БД (только SELECT).** `make prod-sql SQL="..."` — строки `grade_history` по дате/ученику,
   очереди, маркеры в `settings`. Записать id проблемных строк.
3. **Корень в коде.** Найти функцию и условие; спросить «почему не поймали раньше» (тест был, но не на этот
   сценарий? сезонность?). Проверить, не тайм-бомба ли это для тестов (даты «сегодня − N»).
4. **Срочная мера.** Что сделать до фикса (удалить ложные строки, отключить job) — команды выдать
   владельцу с дедлайном (вечерняя сводка 19:00, утренний flush 07:00, полночь = новый «сегодня»).
   Самому прод не менять.
5. **Фикс.** Ветка `fix/<slug>` от `main`; регрессионный тест, воспроизводящий инцидент дословно
   (данные из п.1–2, фиксированные даты); `make test`. Defense-in-depth приветствуется (второй рубеж).
6. **Документы.** `Docs/plans/YYYY-MM-DD-<slug>.md`: инцидент → корень → runbook → дизайн → backlog;
   пункт в CLAUDE.md «Конвенции и подводные камни» (одним абзацем, с датой инцидента); при
   продуктовом характере — бенчмарк аналогов (субагент с WebSearch).
7. **PR** (см. `/gs-pr`) с секцией Runbook и порядком действий на проде. Merge — владелец.
8. **Память:** файл `incident-<slug>-<date>.md` (type: project) + строка в MEMORY.md.

Примеры: `Docs/plans/2026-09-02-academic-year-rollover.md` (прошлогодние оценки при смене учебного года),
инциденты 21.05.2026 (race cell_reference) и 22.05.2026 (importer писал будущие даты) в CLAUDE.md.
